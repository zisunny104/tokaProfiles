# Nukkit 插件拆分與搬遷主文件

更新：2026-10-16。**這是唯一維護整體拆分進度、功能歸屬與後續計畫的文件。** 各專案 README 只說明自己的安裝、設定與 API，不再各自維護一份拆分表。舊盤點入口僅保留連結；歷史驗證紀錄不代表目前正式服已全面驗收。

適用平台以 Nukkit 為範圍；PM1E 是先前使用的測試分支，不是官方 Nukkit 的同義詞，也不是唯一目標。現行正式服使用自行編譯的 Nukkit，檔名 `Nukkit.jar`。不同核心與版本仍需依實際功能驗證。

## 現有依賴與部署原則

- zero 1.7.12 起內嵌 ORMLite 與 MySQL driver，`database.mode` 可用 auto、dblib、embedded-mysql、disabled。正式抽換時選用 embedded-mysql，沿用 `plugins/DbLib/config.yml` 與原 MySQL 資料表；**移除 DbLib JAR 不等於資料搬去 SQLite**。
- one 已由 tokaDiscordLink 接替，不同時執行同一 Bot 的兩個連線服務。one 的 Token／頻道設定已於抽換時複製，舊設定保留。zero 不再直接依賴 one 類別。
- 新插件的正式資料原則為 SQLite／JSON／YAML，預設 SQLite；設定維持 YAML。格式切換使用明確搬遷工具，不能只改 backend 後把空資料視為成功。
- tokaStorage 是 library。SQLite driver 必須依宿主打包方式隔離，保留完整 native resource；不能假設每個舊 JAR 都已升級或隔離。0.1.3 修正空 SQLite 檔案初始化；陌生非空資料庫仍須拒絕開啟。
- 傳輸、身分、世界與區域採小型公開 API／事件。每份有效資料只有一個寫入權責者；可選服務未就緒時停用對應能力，保護資料未就緒不能當作沒有保護。
- 不再把所有失效都升級為整個插件停用。模組要有可查狀態；需要交易或授權時則保守拒絕，不建立假餘額或猜測身分。

## Profiles、Plan 與資料衝突

UUID 為穩定識別，名稱是查詢索引／相容別名。依使用者決策，**已由 Plan 確認的 UUID／目前名稱對照優先使用**；Plan 尚未對照的資料保留舊名稱相容與待轉換標記。Plan 不接管餘額、領地或授權，也不使用通用 Mojang UUID 查詢替 Nukkit 玩家猜 UUID。

本地已有 `PlanResolution` 離線對照工具，可產生有效來源、衝突歷史、待處理與雜湊紀錄；不是已上線的 Plan 自動同步服務。Plan 的玩家 UUID／名稱與暱稱紀錄用途不同，不能把顯示暱稱當成經驗證的帳號名稱。

- 已確定保留身分的衝突 ID，另一筆完整封存並記錄替代關係，避免反覆成為同一筆待決衝突。
- 不以最後登入時間或帳號多久沒使用作淘汰條件；不是把所有舊帳號一起封存。
- Plan 未提供唯一對照、不同業務欄位有衝突或引用尚未核對時，保留待處理；不自動合併金錢、提高權限或覆蓋 Discord 綁定。
- 正式刪除衝突 ID 前，先確認領地、紀錄、Portal、權限與其他引用已轉接；**正式 SQL 刪除與定期清理尚未完成**。
- 來源快照、Plan 證據與背景搬遷 checkpoint 要保存；先建立待啟用資料集，驗證後下次重啟才切換。失敗保留原來源，不部分啟用。
- 稱號可用 legacy／profiles／disabled 轉接；跨儲存扣款交易未完成前，不把付費稱號直接當成可切換功能。
- 舊名稱尚未轉換的所有權顯示可標記；顯示標記不能代替授權或自動變更擁有者。

## 區域模型與權限：保留提案，等待討論

Area、Region、Land 並非完全相同：公共設施、行政／村落政策與私人領地共用範圍模型，但不強迫每種區域都有 owner、售價或成員表。共用欄位包含穩定 ID、世界識別、範圍、類型與規則；領地另有擁有者／分享，村落另有居民隸屬。城市通目前不能視為完整城市管理系統。

授權責任：Profiles 管身分／稱號；LuckPerms 預定管全服能力與群組繼承；Regions 管指定區域的角色／所有權；Worlds 管世界生命週期；Plan 只提供統計展示。一般世界管理權不自動得到領地 bypass。

角色預計按 scopeType＋scopeId＋playerUUID 建模，繼承限定範圍並檢查循環；分享者不自動成為主人。操作應以目標資源的位置與 scope 判斷，不能只查玩家腳下位置；重疊規則及拒絕順序要明確，不能取 HashMap 第一筆。角色名稱、能力矩陣與 context 尚待確認，不直接寫死到程式。

qx 舊資料：0 為最高身分，1／2／3 曾以 qx<4 判斷高權限，4 為一般，8 是特殊顯示而非管理能力；負數等異常值不能自動授權。**這不是已批准的 LuckPerms 群組對照**，也不代表所有入口已移除舊判斷。現有 permissions.mode 的有限橋接不等於全面權限切換；Discord 管理入口目前另有 OP 檢查。

未來降級規則：未安裝 LuckPerms 時保留 OP／一般玩家與已確認擁有者基本保護，複雜分享／居民分級／繼承停用且資料保留；已安裝但故障時拒絕進階操作，不能當成未安裝而擴張權限。這是待實作政策，不宣稱現有插件已全部遵循。**本次只更新文件，依使用者要求權限之後討論。**

## 接續順序與驗收界線

1. 先確認現行部署正常：zero 的資料庫／保護模組、Discord 往返、Portal 與 Worlds。已安裝、成功啟用、真實玩家驗收分別記錄。
2. 優先完成 Profiles 的身分對照與單一寫入來源，再逐步轉接稱號、城市通入口與其他呼叫方；不要在未完成前移除 MySQL。
3. 區域先確認完整模型、匯入及差異報告，再切換單一保護實作。不是一個小功能拆一個 JAR。
4. 權限等使用者確認再做；經濟、聊天與操作紀錄依責任邊界逐步處理。
5. 每次只做受影響範圍的必要檢查；有明確錯誤才擴大，不反覆重跑既有驗證。正式替換需停服、必要備份與可回復紀錄。

已知驗證：zero 內嵌 MySQL driver／ORM 曾在 VPS 暫存表通過 CRUD，未修改正式資料列；新核心的單次隔離啟動驗證了無 DbLib／one 時的基本 zero 模組與 Discord SQLite。這**不是完整鏡像全部正式插件／所有資料／真玩家流程的驗收**。Plan 5.9 build 3705 曾因 utf8mb4 唯一索引過長而無法建表，VPS 現已使用 5.8 build 3638；不將該次失敗算入可用部署。
